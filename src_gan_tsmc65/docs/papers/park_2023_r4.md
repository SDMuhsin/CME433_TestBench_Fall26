# Park, Kung & Lee 2023: approximate radix-4 Booth encoder + 4:2 compressor co-design

G. Park, J. Kung and Y. Lee, "Simplified Compressor and Encoder Designs for Low-Cost Approximate
Radix-4 Booth Multiplier", IEEE TCAS-II 70(3):1154-1158, 2023.

Part of the 16-bit round (standalone multiplier bench `syn/mulbench/`, N = 16 main, N = 8 for
the current chip; `mul16_feasibility.md`). No chip flow was run.

## 1. What the paper proposes
- **Signed n x n radix-4 Booth** (n = 16): n/2 rows p_{i,2i+j} of eq. (1) (digit 111 gives a
  zero row, so neg_i = 0 for it), a separate neg_i (+1) square at column 2i, sign extension
  "E E ~E" on row 0 and "~E 1" on the other rows (Fig. 1).
- **Approximate encoder** (Table I, Fig. 2): p~_{i,2i+j} = a_j | b_{2i+1}, one OR gate instead of
  eight; it turns 0 outputs into 1 (positive error), with one negative case (a_j a_{j-1} = 01,
  digit 011). Used for the data bits of the wG least significant columns ("except for the
  sign-related PP elements").
- **Approximate 4:2 compressor** (Table II, eq. 3): sum = p_{4i}, carry = p_{4i+2} p_{4i+3};
  p_{4i+1} is ignored, no cin / cout (negative error). Used in the wA least significant columns;
  half / full adders there stay exact.
- **Balance** (Sec. III-D, Fig. 3 / 4): pick wG, then the wA whose (0, wA) mean error cancels the
  (wG, 0) mean; the paper's points are (10, 10), (12, 12), (14, 14).
- **Tree** (Fig. 1): two stages of 4:2 compressors (rows 0-3 and 4-7 compressed separately to
  four rows, then to two) with exact compressors chained by cin / cout, a final CPA. The last
  row's neg is OR-ed with that row's first bit (the filled square "OR(Neg, PP)" at column 14).
- **Results** (Table III, 28 nm, DC typical, 50 % input activity, exhaustive error metrics):
  NMED 4.37 / 6.08 / 18.52e-6, MRED 1.53 / 5.34 / 18.54e-4, PRED 99.93 / 99.82 / 99.42 %; area
  -29.6 / -37.3 / -46.5 %, power -27.0 / -33.3 / -45.0 %, delay 0.61 vs 0.62 ns, energy -28 /
  -34 / -46 % vs the paper's exact radix-4 Booth (1,393.7 um^2, 1.034 mW, 0.62 ns).

## 2. Reproduction (`src_gan_tsmc65/approx/`)
| File | Role |
|---|---|
| `park.py` | Booth rows of Fig. 1 for any even n (booth.py, strict neg), approximate encoder in columns < wG, the OR(neg, PP) of the last row (`neg_or`), first-stage row groups of four (each neg in the first group with < 4 bits); `park(n, wg, wa, zero_fix, neg_or)` -> `mult.Multiplier` (bit-exact Python model + netlist) |
| `park_tree.py` | exact 4:2 compressor of eq. (2) (cin / cout chain), the approximate compressor of eq. (3), and the grouped Dadda planner (targets 8 -> 4 -> 2) |
| `paper_park2023.py` | Table III (exhaustive), Fig. 3 / 4 distributions, bench-design metrics -> `approx/results/park2023_error.md` |
| `mulbench.py` | bench designs `park_*` for N = 16 and N = 8 (`PARK`) |
| `variants.py`, `gen.py` | 8-bit chip variant `park_5z` (`bench/variants/park_5z.v`) |

The planner is written from Fig. 1 and, for (wG, wA) = (12, 11), places the same cells in every
column that matters for the error: HAs at columns 6-7 (group A) and 10-11 (group B), approximate
compressors at 8-10 (group A, stage 1) and 4-10 (stage 2) with the constant-0 inputs at columns
5 and 9, exact compressors from column 11 up, the FA / HA closing group A's chain (columns
20-21), HAs at stage-2 columns 2-3 and the final rows (neg_0, neg_1 left for the CPA). In the
exact top columns of stage 2 it chains compressors to column 23 and then uses FA / HAs, where
Fig. 1 chains them to column 27; exact either way, so only the starting netlist for DC differs. The stage-2 bit order (which bit is p_{4i}, which
is dropped) is not printed; the order [group-A sums, group-A rest, carries, group-B sums, group-B
rest] puts the neg squares and '0' dots where Fig. 1 draws them and gives the Table III numbers.

**N = 8 scaling**: wG = wA = half of the paper's 16-bit value (5, 6, 7 for 10, 12, 14: the same
fraction of the 2N product columns, cf. the paper's 12-bit (10, 10)). With four Booth rows there
is one group, so the tree is Fig. 1's second stage alone (one 4:2 stage + CPA), and the last
row's neg (column 6) is OR-ed with p_{3,6} as at 16 bits.

- **Table III reproduces within 1.5 %** (NMED, MRED) and exactly in PRED, but only with the
  OR(neg_7, p_{7,14}) bit of Fig. 1. That OR is not exact: for the top digit -A with a_0 = 0 or
  -2A (P = 1/4) both bits are 1 and the OR loses 2^14, a bias of -4,096 that dominates the
  error at (10, 10) and (12, 12) (NMED 0.71 / 3.36e-6 without it). So the paper's "Exact
  Radix-4" row (NMED 0) is not the proposed structure at (0, 0), and the "zero-mean" error of
  Sec. III-D holds only without that OR. Aizaz & Khare 2022 use the same neg-OR on every row
  (`aizaz_khare_2022.md`).
- **Fig. 3** (1 M random pairs, medians): (0, wA) matches (wA = 13 / 14 / 15: -0.16 / -0.35 /
  -0.72e5 vs ~-0.18 / -0.37 / -0.72e5); (wG, 0) matches to wG = 13 (0.16e5) but is 15-20 % above
  the plot at wG = 14 / 15 (0.37 / 0.83e5 vs ~0.31 / 0.69e5). **Fig. 4** boxes match our
  structure *without* the OR ((12, 12): median -800, quartiles -3,700 / +2,500 vs the inset's
  ~0 / -3,500 / +2,700; (14, 14): -8,700, -21,200 / +4,200 vs ~-8,000, -23,000 / 0); with the OR the
  lower quartiles sit 4,096 lower. (15, 14) and (16, 15) are ~0.3-0.5e5 above the plot, as Fig.
  3(a) above wG = 13: the paper's encoder region near column 14-15 must differ slightly
  (undocumented). Full table: `approx/results/park2023_error.md`.

## 4. Bench designs, zero products and the fix
| Design (N = 16) | (wG, wA) | what |
|---|---|---|
| `park_0` | (0, 0) | exact twin: the same rows and 4:2 tree, no OR (= the paper's "Exact Radix-4") |
| `park_10`, `park_12`, `park_14` | paper points | the paper's design (with the OR) |
| `park_10z`, `park_14z` | (10, 10), (14, 14) | + zero-safe encoder (not in the paper) |
| N = 8: `park_0`, `park_5`, `park_6`, `park_7`, `park_5z` | halved | same, scaled |

**Zero products.** b is the Booth-recoded operand (b = activation in the chip). The paper's
encoder gives p~ = a_j for the digit 000, so **a x 0 != 0** for 65,472 / 65,536 (10, 10) and
65,532 / 65,536 (14, 14) values of a (8 bits: 248-254 / 256), and the GAN-like stream (65 %
zero activations) gets 65 % of its zero products wrong. **Minimal fix (`*z`)**: p~ = b_{2i+1} |
a_j (b_{2i} | b_{2i-1}) (an AO21 per approximate bit, one OR per row): a zero digit gives a zero
row, so b = 0 gives exactly 0; Table I is unchanged elsewhere. **0 x b is not fixed**: with a = 0
the rows of negative digits are all ones (exact Booth) and the AND compressor drops bits, and the
encoder sets digit 111's row to ones; 96-99 % of 0 x b are wrong at (10, 10)-(14, 14) (8 bits:
69-88 %), also in the paper's design. Fixing that needs a zero detector on a (not minimal);
weights are rarely exactly 0 at 16 bits.

### Reading
- **Relative to its own exact twin the paper's trend holds, and is larger.** park_10 / 12 / 14
  are -22 / -30 / -38 % area (paper -30 / -37 / -47 %) and -38 / -44 / -51 % uniform power
  (paper -27 / -33 / -45 %) below `park_0`, and 13-16 % faster (paper: equal delay).
- **The hand-written exact Booth + 4:2 tree is the problem**, as with `booth_axfa5` at 8 bits:
  `park_0` is +38 % area, +26 % delay and +87 % uniform power against DesignWare at 16 bits
  (+34 % area at 8 bits). DC does not restructure a gate-level XOR / mux compressor tree into its
  own Booth-Wallace. Only from (12, 12) up does the approximation save more than that overhead.
- **GAN-like power** falls 33-51 % at 16 bits, and that is the approximation, not the structure:
  `park_0` is +8 % there (a zero activation gives zero Booth rows in both). At 8 bits `park_0`
  alone is -29 % (GAN-like), so most of `park_5z`'s -44 % is the structure.
- Delay: every 16-bit variant is 6-11 % slower than DesignWare and needs a 5-8 % longer min
  period; all meet 2.5 ns with margin. At 8 bits park_5..7 are 1.5-4 % faster.

## 6. Verdict (16 bits, 400 MHz, vs `s_exact`)
| Variant | >= 1 positive hardware metric? | which |
|---|---|---|
| `park_10` | yes, one | GAN-like power -33 % (uniform +16 %, area +8 %, delay +10 %) |
| `park_12` | yes | area -2.9 % (-9.2 % at 4.0 ns), GAN-like power -39 % |
| `park_14` | yes | area -14.4 %, uniform power / energy -8.2 %, GAN-like power -47 % |
| `park_10z` | yes, one | GAN-like power -37 % |
| `park_14z` | yes | area -14.0 %, uniform power / energy -13.5 %, GAN-like power -51 % |

No relaxed-clock rescue is needed for (12, 12) / (14, 14); for (10, 10) the 4.0 ns area is still
+3.7 % (the -22 % approximation saving cannot pay for the +38 % structure). For a 16-bit chip
(multipliers ~12-20 % of area, ~4 % of power, `mul16_feasibility.md` s.6) park_14z would give
about -1.7 to -2.8 % chip area and ~-0.5 % (uniform) to -2 % (GAN-like) chip power, at
MRED 0.17 % and a GAN-like bias of -6,000 per product (4e-4 of the mean |product|). Unlike the
signed CDM16 and the HAM, this design is signed-native and adds no serial stage, so it keeps a
real area and power gain over DesignWare at 400 MHz; the delay is the cost. The paper's design
itself (without `z`) is not usable on the GAN chip: two thirds of its products (all zero
activations) are wrong. At 8 bits the chip variant `park_5z` (bench smoke test `run_bench.sh
park_5z --n 16`: RTL == Python 16/16 images, PSNR 29.2 dB vs golden, 16/16 labels) is
area-neutral and +14 % uniform power vs exact; only `park_6` / `park_7` save area.

```
python3 -m src_gan_tsmc65.approx.paper_park2023            # Table III exhaustive (~25 min, 44 cores)
python3 -m src_gan_tsmc65.approx.mulbench --width 16       # RTL (also --width 8)
python3 -m src_gan_tsmc65.approx.mulbench_check --width 16 # RTL == model
python3 -m src_gan_tsmc65.approx.gen                       # bench/variants/park_5z.v
src_gan_tsmc65/syn/mulbench/start.sh w16_park.log 16 3 park_0 park_10 park_12 park_14 park_10z park_14z
src_gan_tsmc65/syn/mulbench/start.sh w8_park.log 8 3 park_0 park_5 park_6 park_7 park_5z
python3 -m src_gan_tsmc65.approx.mulbench_table --width 16  # after copying the summaries
```
Six 16-bit designs took ~45 min on the server with three in parallel, five 8-bit designs ~25 min.
