# Zhu et al. 2022: approximate radix-256 Booth encoding (AR256)

F. Zhu, S. Zhen, X. Yi, H. Pei, B. Hou and Y. He, "Design of Approximate Radix-256 Booth Encoding
for Error-Tolerant Computing", IEEE TCAS-II 69(4):2286-2290, 2022.

Paper B of the 16-bit round (standalone multiplier bench `syn/mulbench/`, N = 16 main, N = 8 for
the current chip; `mul16_feasibility.md`, `park_2023_r4.md`). No chip flow was run.

## 1. What the paper proposes
- **Hybrid Booth encoding** (Fig. 1), signed n x n (n = 16): the 8 LSBs of the multiplier Y
  (plus y_-1 = 0) form one radix-256 digit d_k in [-128, 128] (eq. 4), the upper n - 8 bits use
  exact radix-4 Booth, (n - 8) / 2 rows (the first overlapping y_7). 16 x 16: 2 + 4 = 6 rows
  instead of 8.
- **Partial encoding** (Table III): only the top 4 bits t = y_7 y_6 y_5 y_4 of the 9-bit set are
  encoded; each of the 16 sections (17 digit values) is replaced by one P_k = PPA + PPB with
  PPA, PPB powers of two times X (no hard multiple), chosen for the smallest maximum error
  (MAE 8X or 16X per section, eq. 5). Two encoders (eqs. 6-7) select {16, 32, 64}M and
  {8, 16, 32, 64}M; PPA_j / PPB_j are AND-OR selections of shifted X bits XOR-ed with
  c = y_7 (eq. 8, Fig. 2), plus the correction bits c.
- **Tree**: "the same compression tree with exact 4-2 compressors and carry propagation adders"
  for all designs, gate-level Verilog, DC, 0.18 um, 100 MHz.
- **Results** (Table V): AR256 NMED 0.460e-4, MRED 0.19 %, PRED 99.02 %; vs the exact radix-4
  ACR4 area -42.39 %, delay -7.03 %, power -26.00 %, energy -31.2 % (25,659 -> 14,782 um^2,
  7.11 -> 6.61 ns, 6.197 -> 4.586 mW). Unit-gate estimate (Table IV) 0.79 of ACR4.

| `zhu.py` | `zhu(n, d, zero_fix)` -> `mult.Multiplier` (PPA / PPB rows, exact radix-4 rows from `booth.py`, sign extension by constant via `matrix.py`, one group of exact 4:2 compressors from `park_tree.py`, one CPA); `Model` = closed form p = a (b - b_lo + P(b_lo)) |

Notes on fidelity:
- The encoders are written from Table III. The printed eqs. (6)-(7) lost overbars in places
  (A_32M as printed is also 1 for t = 0100, where A_64M is selected); B_8M and A_64M as printed
  agree with the table. Table III itself is self-consistent and reproduced exactly (all 16
  sections: digit range, PPA, PPB, P_k, MAE).
- Fig. 2 computes PPA_j / PPB_j down to j = 0, where the shifted X bits are 0 and the bit is
  0 xor c = c; with the correction c at column 0 these bits sum to c 2^shift, so the generator
  puts c at the row's smallest shift (identical value, no constant-0 columns). The row sign bit
  is (x_15 AND any select) xor c as in Fig. 2 (PPA_MSB), so "-0" (t = 1111) gives exactly 0.
- The exact radix-4 twin (ACR4: exact radix-4 Booth, exact 4:2 tree, CPA) is the bench's
  `park_0` (paper A), already measured.

**Width parameter / N = 8 scaling.** The AR digit width d is a parameter (d even, 6 <= d <= n):
the d LSBs form one approximate digit, its top 4 bits are encoded with the same Table III and
every multiple is scaled by 2^(d-8) (d = 8 is the paper; the encoder logic is unchanged, only
the X shifts move). At N = 8 the paper's d = 8 covers the whole operand (two rows, no radix-4
row: b collapses to 16 levels, MRED 21.5 %), so the bench also uses d = 6 (radix-64 digit on
b[5:0] plus one radix-4 row for b[7:6], the 16-bit design's mix of one AR digit + exact rows).
At N = 16, d = 6 / 10 are less / more aggressive points around the paper's d = 8 (7 / 5 rows).

| AR256 paper (Table V) | - | 4.60e-5 | 0.19 % | 99.02 % | - | - |

| d = 10 + zero fix | 3.657e-4 | 1.829e-4 | 0.772 % | 96.28 % | 98.73 % | 2,097,152 |

- **MRED matches (0.186 vs 0.19 %), NMED matches within 0.5 % if normalised by 2^31** (the paper
  evidently divides by 2^31, not by the largest product 2^30; with 2^30 ours is exactly 2x),
  **PRED is 0.06 points higher** (99.08 vs 99.02 %). The relative error depends only on b
  (|E| / |exact| = |e(b)| / |b|), so the gap is not a metric-convention issue for a; the paper's
  "16-bit random input data" may have been a random sample (the PRED gap is ~2 sigma of a 10^5
  sample). The overall mean error is -0.25 (essentially unbiased): the section errors are
  symmetric, the "more symmetrical error distribution" of Sec. VI.
- Netlist == closed-form model on all 65,536 pairs at N = 8 and 4 M random pairs at N = 16 for
  every design; Table V of the other papers' designs (ABM1-14, R4ABM14, HLRBM2, RAD256) and the
  DCT application were not reproduced.

## 4. Bench designs, zero products and the fix
| Design | N | d | what |
|---|---|---|---|
| `r256_8` | 16 | 8 | the paper's AR256 multiplier |
| `r256_8z` | 16 | 8 | + zero-safe B_8M (not in the paper) |
| `r256_6z`, `r256_10z` | 16 | 6, 10 | scaled Table III (x 2^-2 / x 2^2) + zero fix |
| `r256_6`, `r256_6z` | 8 | 6 | radix-64 AR digit + one radix-4 row (chip variant `r256_6z`) |
| `r256_8`, `r256_8z` | 8 | 8 | the paper's AR256 digit alone |

**Zero products.** b is the recoded operand (the activation in the chip). Section t = 0000
gives P = 8X, so **a x 0 = 8a != 0** for every a != 0 (65,535 / 65,536; 8 bits 255 / 256),
and any b with b[7:0] = 0 is off by 8a. **0 x b = 0 always** (a = 0 makes every selected
multiple 0, and the one's complement plus c is exact). **Minimal fix (`*z`)**: B_8M AND
OR(b[0..d-1]) (one d-input OR and one AND): the zero digit then gives P = 0, Table III is
unchanged elsewhere, so b = 0 gives exactly 0 (and a x 0 = 0 for all a); the error metrics
barely move (MRED 0.186 -> 0.185 %), but the GAN-like MAE falls 3.5x (47,700 -> 13,800).

### Reading
- **Against its own exact radix-4 twin the paper's trend holds**: `r256_8` is -31 % area
  (paper -42 %), -35 % uniform power (paper -26 %) and -11 % delay (paper -7 %) below `park_0`.
  The area saving is smaller than the paper's (presumably the 0.18 um wire-load flow weights
  the removed rows / compressors differently; not investigated).
- **Against DesignWare the structure overhead (+38 % area, +87 % uniform power for the
  hand-written exact Booth + 4:2 tree) eats most of it**: `r256_8` saves only 4 % area (7 % at
  4.0 ns) and costs +22 % uniform power and +13 % delay; GAN-like power is -22 % (-29 % with
  the zero fix, since a zero activation now gives two zero rows instead of an 8a row).
- The zero fix is not free at 16 bits: `r256_8z` is +3 % uniform power and +2.5 % delay over
  `r256_8` (8-input OR in the B_8M path); its 4.0 ns area (+2.2 %) is DC variance (`r256_8` at
  4.0 ns: -7.0 %). At 8 bits the 2.5 ns area of `r256_6z` (-1.0 %) vs `r256_6` (-9.1 %) is
  the same kind of DC variance (both -11 to -12 % at 4.0 ns).
- **Only the coarser d = 10 point recovers the overhead in uniform power** (-3 %), at 4x the
  error (MRED 0.75 %); d = 6 (MRED 0.045 %) is worse than DesignWare everywhere except GAN-like
  power.
- **vs paper A at equal accuracy**: `park_14z` (MRED 0.173 %) is -14 % area, -13.5 % uniform
  and -51 % GAN-like power; `r256_8z` (MRED 0.182 %) is -4 % / +26 % / -29 %. The radix-4 +
  approximate encoder / compressor route is the better 16-bit design at this accuracy.

## 6. Verdict (16 bits, 400 MHz, vs `s_exact`)
| Variant | >= 1 positive hardware metric? | which |
|---|---|---|
| `r256_8` (paper) | yes | area -4.1 % (-7.0 % at 4.0 ns), GAN-like power -22 %; uniform power +22 %, delay +13 % |
| `r256_8z` | yes | area -3.7 %, GAN-like power -29 %; uniform power +26 %, delay +16 % |
| `r256_6z` | yes, one | GAN-like power -11 % only (area +18 %, uniform power +53 %) |
| `r256_10z` | yes | area -22.7 %, uniform power / energy -3.1 %, GAN-like power -46 %; delay +3.5 %, MRED 0.75 % |

The design is signed-native and adds no serial stage (its rows are shifts of X, no hard
multiple), so it keeps an area and GAN-like power gain over DesignWare at 400 MHz, but at the
paper's accuracy the gain is small and uniform-input power is worse; it is dominated by
`park_14z`. The paper's design itself is not usable on the GAN chip without the `z` fix
(a x 0 = 8a for all zero activations). At 8 bits the chip variant `r256_6z` is area-neutral
(-11 % at 4.0 ns), power-neutral (uniform) and -57 % GAN-like power, at MRED 5.1 % (vs 3.1 %
for `park_5z`); bench smoke test `run_bench.sh r256_6z --n 16`: RTL == Python emulation 16/16
images, PSNR 25.5 dB vs golden (park_5z: 29.2 dB), labels 16/16 (result file not committed).
`r256_8` at 8 bits is small (-36 % area) only because it ignores b[3:0] (MRED 21.5 %).

